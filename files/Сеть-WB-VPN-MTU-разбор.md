# Сеть, VPN и MTU: почему «не искало» фото WB — разбор для изучения

> Заметка-эпопея: как из «`--photos-only` не работает» мы дошли до «у VPN-туннеля
> неправильный MTU». Ниже — не только что было, но и **концепции, которые стоит доучить**
> (помечены 📚), и переиспользуемый **план диагностики**. Читать сверху вниз.

## TL;DR (два вывода)

1. **Причина затыка — MTU VPN-туннеля.** `tun0` был с `mtu 1500`. Туннель добавляет свои
   заголовки, поэтому реальный «умещающийся» размер меньше 1500. Большой пакет
   (TLS-приветствие ~1.5 КБ) не влезал и **молча терялся** → TLS-рукопожатие висело →
   таймаут. Мелкие пакеты (установка TCP) проходили — потому и «подключается, но виснет».
2. **VPN для фото/ИНН вообще не нужен.** Хосты `card.wb.ru` (шаг `wb`) и
   `basket-*.wbbasket.ru` (фото) отвечают и **без** VPN, мгновенно. Российский IP нужен
   ТОЛЬКО шагу `search` (там `search.wb.ru` отдаёт пусто с иностранного IP). То есть
   туннель нам не помогал, а мешал.

## Часть 1. Что происходило (хроника)

1. `python run.py 9_flacons search --photos-only` → «8 сетевых ошибок подряд», фото 0.
2. `curl -v https://basket-18.wbbasket.ru/` → доходит до отправки `Client hello [1576 bytes]`,
   потом **`Connection timed out after 8001 ms`**. То же с `card.wb.ru`.
3. `dig` показал, что **имена резолвятся** (IP получены) → значит проблема не в DNS, а в
   доставке пакетов.
4. `ip route get 185.62.202.24` → `via 172.18.0.2 dev tun0 table 2022` → весь трафик к WB
   идёт **через VPN-туннель** `tun0`.
5. Оказалось `search.wb.ru` и `card.wb.ru` — **один и тот же IP** `185.62.202.24`. Значит
   «search работает, а фото нет» — иллюзия: карточки собраны в прошлой сессии, а сейчас
   через туннель не идёт ничего к WB.
6. **С полностью выключенным VPN**: `card` → `HTTP 307 за 0.077s`, `basket` → `404 за 0.068s`.
   Работает мгновенно! → значит виноват туннель, а не провайдер и не WB.
7. `ip link show tun0` → **`mtu 1500`**. Для туннеля это подозрительно много.
8. `sudo ip link set tun0 mtu 1280` → но VPN-клиент **откатывал** обратно на 1500, а правки
   «на ходу» роняли интерфейс (`curl` → `000 0.000000`, мгновенный сбой).
9. Вывод: править MTU руками бесполезно (клиент управляет `tun0`); чинить — в конфиге
   клиента; а для фото — просто выключить VPN.

## Часть 2. Концепции для изучения (это и есть план)

### 2.1. VPN-туннель и интерфейс `tun0`
VPN создаёт **виртуальный сетевой интерфейс** (`tun0`). Трафик, «завёрнутый» в него,
шифруется и уходит на VPN-сервер, который дальше идёт в интернет от своего имени
(своего IP). `POINTOPOINT` в `ip link` = «точка-точка»: у туннеля один собеседник (сервер,
у нас `172.18.0.2`).
🔍 *У нас*: все пакеты к WB заворачивались в `tun0`.
📚 *Изучить*: что такое tun/tap-интерфейсы; чем WireGuard отличается от OpenVPN.

### 2.2. Маршрутизация по правилам (policy routing): `table 2022`, `uid 1000`
В Linux не одна таблица маршрутов, а много. **`ip rule`** выбирает таблицу по условию.
Строка `table 2022 ... uid 1000` значит: «трафик пользователя с uid 1000 → таблица 2022 →
через `tun0`». Так делают **сплит-туннель** («гнать через VPN только это»).
🔍 *У нас*: именно это правило отправляло WB (и, похоже, весь трафик uid 1000) в туннель.
📚 *Изучить*: `ip rule`, `ip route show table N`, чем split-tunnel отличается от full-tunnel.

### 2.3. DNS ≠ маршрут ≠ доступность
Три разных шага, которые легко спутать:
- **DNS** (`dig name`) — имя → IP. У нас работал.
- **Маршрут** (`ip route get IP`) — каким интерфейсом/шлюзом пойдёт пакет к этому IP.
- **Доступность** — реально ли доходит и отвечает (TCP/TLS).
Можно успешно зарезолвить имя и всё равно **не достучаться** (пакеты дропаются).
🔍 *У нас*: `dig` ок, но соединение виснет → значит проблема ниже DNS.
📚 *Изучить*: разница «резолвится / маршрутизируется / отвечает».

### 2.4. TCP-рукопожатие vs TLS-рукопожатие — где именно висло
- **TCP** (SYN → SYN-ACK → ACK) — крошечные пакеты, устанавливают соединение.
- **TLS** (поверх TCP): клиент шлёт **ClientHello** — он **большой** (~1.5 КБ: список
  шифров, расширения, SNI), сервер отвечает ServerHello…
В `curl -v` мы видели: TCP встал (`Trying …:443`), **ClientHello ушёл** (`[1576 bytes]`),
а ответа нет → таймаут. Т.е. рвётся **на первом большом пакете**. Это ключевая улика.
📚 *Изучить*: этапы TLS-handshake; что такое SNI и почему ClientHello бывает большим.

### 2.5. ⭐ MTU, MSS, PMTUD — сердцевина проблемы
- **MTU** (Maximum Transmission Unit) — максимальный размер одного пакета на канале.
  В Ethernet обычно **1500** байт.
- **MSS** (Maximum Segment Size) — сколько полезных данных TCP влезает в один сегмент,
  ≈ MTU − заголовки (1500 − 40 = **1460**). Договаривается в SYN.
- **Overhead туннеля**: VPN оборачивает каждый пакет в свои заголовки (WireGuard ~60 Б,
  OpenVPN больше). Значит внутренний пакет 1500 Б на «внешнем» канале становится ~1560+ Б —
  **больше реального MTU** → должен фрагментироваться или быть отброшен.
- **PMTUD** (Path MTU Discovery) — механизм, которым отправитель *узнаёт* реальный
  минимальный MTU по пути (через ICMP-сообщения «fragmentation needed»). Если эти ICMP
  **заблокированы** (частый случай) — отправитель не узнаёт, и пакет **молча теряется**.
  Это и есть **«MTU black hole»**.

**Почему у нас TCP вставал, а TLS висел:** SYN/ACK — маленькие, влезали. Первый крупный
сегмент (ClientHello, ~1460 Б → с оверхедом туннеля >1500) не влезал в путь и **терялся**;
ICMP не доходил (blackhole) → клиент вечно ждал ответа → таймаут.

**Почему `tun0 mtu 1500` — это ошибка:** у туннеля MTU должен быть **меньше** 1500 на размер
оверхеда (обычно 1280–1420), чтобы даже обёрнутый пакет влезал во внешний 1500.
🔍 *У нас*: `mtu 1500` на `tun0` + заблокированный PMTUD = потеря больших пакетов.
📚 *Изучить (самое важное в заметке)*: MTU vs MSS; PMTUD и «чёрные дыры»; почему
`mtu 1280` почти всегда безопасен; что такое **MSS clamping** (`--clamp-mss-to-pmtu`).

### 2.6. Почему ручной `ip link set mtu` не помог
VPN-клиент (wg-quick / openvpn / GUI) сам **управляет** `tun0` и при каждом
(пере)подключении **заново ставит свой MTU** из конфига, затирая ручные правки. Правки
«на лету» ещё и роняли интерфейс в переходное состояние.
✅ *Правильно*: задавать MTU **в конфиге клиента** (WireGuard `MTU = 1280`; OpenVPN
`tun-mtu`/`mssfix`), а не через `ip link`.
📚 *Изучить*: кто «владелец» интерфейса; идемпотентность сетевых конфигов.

### 2.7. Как читать результат `curl`
Наш приём: `curl -s -o /dev/null -w "%{http_code} %{time_total}\n" --max-time 10 URL`.
- `307/200 за <1s` — хост ответил, всё живо.
- `000 за ~10s` — **таймаут** (пакеты уходят в никуда — как при MTU-blackhole).
- `000 за 0.000000` — **мгновенный сбой** ещё до сети: нет маршрута / не резолвится /
  интерфейс в переходном состоянии. **Это НЕ таймаут** — другой класс проблемы.
- `curl … ; echo "exit=$?"`: `28`=таймаут, `6`=DNS, `7`=нет маршрута/refused.
📚 *Изучить*: коды выхода curl; формат `-w` (`%{...}` переменные).

### 2.8. WB-специфика: кому нужен российский IP
- **`search.wb.ru`** — гео-фильтрует: с иностранного IP отдаёт **пусто** → нужен РФ-IP.
- **`card.wb.ru`** (ИНН, шаг `wb`) и **`basket-*.wbbasket.ru`** (фото) — отдают **всем**,
  РФ-IP не требуется.
Отсюда вывод: `--photos-only` и `wb` можно гонять **без VPN**; VPN нужен только `search`.
📚 *Изучить*: как сайты гео-фильтруют (по IP-геолокации на конкретных эндпоинтах).

## Часть 3. Диагностический плейбук (переиспользовать)

Воронка «сужаем, где рвётся»:
1. **Симптом точно?** — `curl -v URL`: где встаёт (`Trying` → TCP; `Client hello` → TLS).
2. **DNS или доставка?** — `dig +short name`. Резолвится? Тогда дело не в DNS.
3. **Каким путём идёт?** — `ip route get <IP>`. Через VPN (`dev tun0`) или напрямую?
4. **VPN виноват?** — выключить VPN и повторить `curl`. Заработало без него → туннель.
5. **Таймаут или мгновенный сбой?** — `%{time_total}`: `~timeout` (доставка/MTU) vs
   `0.000000` (маршрут/DNS/переходное состояние).
6. **Похоже на MTU?** — признак: **TCP встаёт, но первый большой пакет (ClientHello) виснет**.
   Проверка: `ip link show tun0` (MTU 1500 на туннеле = подозрительно); тест — временно
   `mtu 1280` и сразу `curl` (одной `&&`-строкой, пока клиент не откатил).
7. **Чинить в нужном месте** — не `ip link` (затрётся), а конфиг VPN-клиента / MSS-clamp /
   обойти VPN для этих хостов.

## Часть 4. Шпаргалка команд

```bash
# что и куда резолвится
dig +short card.wb.ru
# каким интерфейсом пойдёт пакет к IP
ip route get 185.62.202.24
# MTU и состояние туннеля
ip link show tun0
# чистый вердикт доступности (без «портянки»)
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" --max-time 10 https://card.wb.ru/
# точный класс ошибки
curl --max-time 10 https://card.wb.ru/ ; echo "exit=$?"   # 28=timeout 6=DNS 7=no route
# временно понизить MTU и сразу проверить (одной строкой)
sudo ip link set dev tun0 mtu 1280 && curl -s -o /dev/null -w "%{http_code} %{time_total}\n" --max-time 10 https://card.wb.ru/
# durable-фикс (WireGuard): в [Interface] -> MTU = 1280, затем wg-quick down/up
# durable-фикс (OpenVPN): tun-mtu 1400 + mssfix 1360
```

## Часть 5. Глоссарий

- **MTU** — макс. размер пакета на канале (Ethernet: 1500).
- **MSS** — макс. полезная нагрузка TCP-сегмента (≈ MTU − 40).
- **PMTUD** — обнаружение MTU по пути через ICMP; при заблокированном ICMP → «чёрная дыра».
- **MSS clamping** — принудительно занизить MSS в SYN, чтобы сегменты гарантированно влезали.
- **tun0** — виртуальный интерфейс VPN-туннеля.
- **policy routing** — выбор таблицы маршрутов по правилам (`ip rule`), основа сплит-туннеля.
- **split-tunnel** — через VPN идёт только часть трафика.
- **ClientHello** — первый (большой) пакет TLS от клиента.
