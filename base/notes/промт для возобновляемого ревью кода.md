Замена [[промт для ревью кода|v1]]. v1 запускал multi-agent воркфлоу: качественно, но сжигает лимит сессии с 0 до 100%, а воркфлоу не возобновляется в новой сессии ([[особенности claude code workflows]]). v2 меняет механику: ревью идёт батчами ≤10 файлов, после каждого батча прогресс и находки дописываются в файлы репозитория.

Промт возобновляем по построению: первым действием он читает прогресс-файл, поэтому после вылета по лимиту достаточно открыть новую сессию и вставить **тот же самый промт целиком** — отдельная фраза «продолжи» не нужна. Предохранитель «{N} батчей и стоп» не даёт выжечь лимит за один присест (на Pro ставь N = 3–4).

Основной промт (Sonnet 5, effort xhigh):

> Проведи ревью репозитория {РЕПО} батчами. Только ревью — ничего не исправляй и не редактируй код.
>
> Первым делом прочитай docs/review-progress.md.
> - Если файла нет: разбей репозиторий на батчи по директориям/модулям (≤10 файлов исходников в батче), запиши в docs/review-progress.md список батчей со статусом pending, а в шапку docs/refactor-backlog.md скопируй правила поиска и формат записи из этого промта.
> - Если файл есть: done-батчи не перечитывай, продолжай с первого pending.
>
> Что искать в каждом батче:
> 1. Баги и логические ошибки — только реальные, с конкретным сценарием воспроизведения, без спекулятивных «может быть».
> 2. Компоненты-переростки под декомпозицию.
> 3. Дублирование — в т.ч. mobile/desktop-ветки, сводимые к одной адаптивной реализации.
> 4. Стаб-хуки, мёртвый и недописанный код.
> 5. Архитектурные слабости: границы слоёв, обработка ошибок, ретраи, кэши.
>
> После КАЖДОГО батча, не дожидаясь конца: допиши находки в docs/refactor-backlog.md (запись: проблема, файл:строка, почему важно, оценка усилия S/M/L; группировка P1 баги → P2 быстрые победы → P3 крупные рефакторинги) и переведи батч в done в docs/review-progress.md. Эти два файла — единственное хранилище прогресса: сессия может оборваться в любой момент.
>
> Сделай {N} батчей и остановись: покажи краткую сводку и жди команды. Ложное срабатывание хуже пропуска — сомнительное не записывай.

Адверсариальная проверка — когда все батчи done, отдельной сессией на Opus 4.8 ([[адверсариальная верификация]]):

> Прочитай docs/refactor-backlog.md. Для каждой находки попробуй её опровергнуть: открой указанный код и проверь, существует ли проблема на самом деле и воспроизводится ли описанным сценарием. Неподтверждённые записи помечай зачёркиванием с причиной в скобках, подтверждённые — ✅. Код не исправляй. Ложное срабатывание хуже пропуска.
