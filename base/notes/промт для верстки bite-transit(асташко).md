Короткий ответ: Sonnet 5 с этой вёрсткой справится — при условии жёсткого промта с циклом визуальной сверки. Opus имеет смысл подключать точечно, не как основную модель.

Почему Sonnet 5 хватит именно здесь:

- По коду и агентной работе Sonnet 5 — почти уровень Opus (это его главное отличие от Sonnet 4.6), поддерживает effort xhigh — режим, рекомендованный для кодинга.
- У него то же зрение высокого разрешения, что у Opus 4.8 (до 2576px по длинной стороне) — критично для сравнения скриншотов Figma с результатом.
- Вёрстка 18 секций + 15 страниц — это много длинных однотипных итераций со скриншотами (картинки жрут токены): Sonnet 5 в 2.5 раза дешевле Opus ($3/$15 против $5/$25 за млн токенов, а до 31.08.2026 действует интро-цена $2/$10).
- Твоя задача идеально структурирована: правила в CLAUDE.md/STYLEGUIDE.md, узлы и методика в ROADMAP.md/docs/pages/. Sonnet 5 следует инструкциям буквально — на такой задаче это плюс.

Где Opus 4.8 реально лучше: длинные автономные прогоны без присмотра (несколько секций за один заход «на ночь»), неоднозначные места макета, требующие дизайн-суждений (bento-сетка features, квиз), и ревью-проходы (этап 4). Практичная схема: секции верстает Sonnet 5, ревью и пиксель-сверку этапа 4 гоняешь на Opus (/model переключает в любой момент). Важная оговорка: качество «пиксель-в-пиксель» определяется не столько моделью, сколько наличием в промте обязательного цикла «скриншот Figma → вёрстка → скриншот localhost → сравнение → правка» и проверяемого Definition of Done — Sonnet 5 с таким циклом обгонит Opus без него.

Промт (шаблон на одну секцию — запускай по одной, подставляя имя):

Сверстай секцию «{СЕКЦИЯ}» главной страницы «Байт Транзит» пиксель-в-пиксель по макету Figma.

Перед началом прочитай и считай обязательными: CLAUDE.md, docs/STYLEGUIDE.md,
docs/ROADMAP.md (методика этапа 1), docs/pages/page-homepage.md (Y-бэнд, тёмность,
заметки этой секции), строку секции в docs/PLAN.md.

Источник истины — Figma pHURPgbJ8aV2eKZNI4PxQa, страница «сайт» (64:202):
десктоп — артборд «главная» 107:6 (1920px), мобайл — фрейм «2» 317:10756 (320px).
Файл — концепт с устаревшими итерациями: работай ТОЛЬКО с этими узлами.
Секцию изучай визуально (скриншот узла по Y-бэнду) + design-context для точных
размеров/цветов/шрифтов. Сырые метаданные канваса не реверсить.

Порядок работы:
1. Отрендери секцию из макета. Выпиши структуру, ВСЕ тексты дословно (ничего не
	 сочинять), размеры, цвета. Сверь значения со STYLEGUIDE — в коде только
	 CSS-переменные из src/scss/variables/, хардкод hex/px запрещён.
2. Ассеты в src/img/{секция}.bit/: контентные ×2, декоративные ×1, иконки — SVG
	 с currentColor, скругления у фото снять перед экспортом, свечения/ореолы — на CSS.
3. Разметка: tpls/sections/{секция}.html + недостающие карточки в tpls/cards/.
	 Максимально переиспользуй components.b/components.bit (button, input,
	 паттерн div.__media > picture.__media-pic > img.__media-img). БЭМ строго,
	 «внуки» block__a__b запрещены. Формы — без тега <form>, со скрытым form_name.
4. Стили: ОДИН файл src/scss/sections.bit/_{секция}.scss, скобки без нестинга,
	 только em/rem (1rem = 10px при 1920), height → min-height,
	 position:absolute — только декор.
5. ОБЯЗАТЕЛЬНЫЙ цикл сверки (не пропускать): npm start → скриншот секции
	 с localhost:3000 (headless-браузером) → сравни со скриншотом узла Figma →
	 перечисли конкретные расхождения (отступы, кегль, межстрочка, цвета,
	 выравнивание, радиусы) → исправь → повтори. Останавливайся только когда
	 расхождения неразличимы на глаз; обычно нужно 2–3 круга.
6. Линты: npx stylelint "src/scss/**/*.scss" и npx htmlhint "src/**/*.html" — чисто.

Definition of Done — отчитывайся только с доказательствами по каждому пункту:
- финальная пара скриншотов (Figma / localhost) совпадает — приложи обе;
- тексты дословно из макета;
- grep по твоему диффу: нет px, нет hex вне variables/, нет height,
	нет inline style, нет block__a__b, нет классов с префиксом bx-;
- линты зелёные, npm run prod зелёный.
Если какой-то пункт не сошёлся — скажи прямо, что именно и почему, не пиши «готово».
Скоуп — только эта секция: соседние секции, доки и чужие стили не трогать.

Пара практических замечаний к запуску: держи одну секцию на сессию/задачу (контекст остаётся чистым, скриншоты не вытесняют правила), effort в Claude Code по умолчанию xhigh — менять не нужно, а после каждых 3–4 секций имеет смысл отдельный ревью-проход на Opus по свежесвёрстанному (/code-review или промт «проверь секции X, Y на соответствие ТЗ и макету»).
