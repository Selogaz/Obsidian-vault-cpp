Практическое дополнение к [[стратегия расходования usage credits с Fable 5]]: готовый промт архитектурной сессии и правила ведения релизной ветки, при которых `/code-review` даёт максимум.

## Промт архитектурной сессии

Запуск: Fable 5 в plan mode в корне проекта. Своё — в `<...>`.

```text
Проведи архитектурную сессию для фронтенд-проекта. Твоя задача — принять
решения и зафиксировать их в design doc, а НЕ писать код приложения.

Контекст:
- Продукт: <что делает приложение, 3–5 предложений>
- Ключевые сценарии пользователя: <2–4 сценария>
- Стек зафиксирован: <React + TypeScript + Vite / ...>. Менять его нельзя.
- Важно: код по этому документу будут писать более слабые модели, поэтому
  каждое решение должно быть однозначным — без «можно так, а можно иначе».
- Ограничения: <нужен ли SSR/SEO, браузеры, дизайн-система, сроки>

Прими решение по каждому пункту. Формат: решение → почему → отвергнутая
альтернатива и чем она хуже → как проверить, что решение соблюдается.

1. Слой данных: как ходим в API, где живут типы ответов, стратегия
   кеширования и инвалидации.
2. Состояние: что server state, что client state, что URL state; чем
   управляется каждое; что ЗАПРЕЩЕНО класть в глобальный стор.
3. Границы компонентов: структура папок, критерий разделения компонента,
   правила зависимостей между слоями.
4. Единые контракты: формат ошибок API и один общий паттерн
   error/loading/empty states для всех экранов.
5. Маршрутизация и code splitting.
6. Стратегия тестов: что покрываем unit / integration / E2E и какие тесты
   сознательно НЕ пишем.
7. Топ-5 рисков проекта и как архитектура каждый закрывает.

Правила сессии:
- Если контекста не хватает — сначала задай мне до 5 уточняющих вопросов,
  только потом решения.
- Код — только короткие иллюстрации контрактов (типы, сигнатуры),
  не длиннее 10 строк на пункт.
- Результат — один файл docs/design.md; сохрани его после моего одобрения.
```

Для **существующего** проекта меняется только шапка: «Сначала изучи кодовую базу (src/, package.json, роутинг, стор). Затем по тем же семи пунктам вынеси вердикт "оставить / изменить" с обоснованием, а в конце дай порядок миграции: что менять первым и почему».

Экономность промта держится на двух свойствах: уточняющие вопросы *до* решений (иначе модель сожжёт токены на решения по выдуманному контексту) и запрет на код — вывод остаётся коротким, оплачивается мышление, а не печать.

## Дифф релизной ветки

`/code-review` никогда не смотрит весь проект — только *дифф*: разницу между веткой и точкой её расхождения с main (`git diff main...ветка`). Стоимость и качество ревью зависят от размера диффа, а не проекта. Релизная ветка — ветка с накопленными изменениями, готовящимися к релизу; её дифф против main и попадает в ревью.

### Правила ведения ветки

1. **Дифф — маленький и тематический.** С ростом диффа внимание модели размазывается и баги тонут в объёме. Перед тратой кредитов — `git diff --stat main...HEAD`; тысячи строк по десяткам файлов — дробить: короткие релизные циклы (1–2 недели) вместо «ревью за квартал».
2. **Регулярно подтягивать main** (rebase или merge из main): дифф показывает только свою работу, без переплетения с чужими изменениями.
3. **Механика отдельно от логики.** Форматирование, переименования, lockfile, кодогенерация — отдельными коммитами до содержательной работы. Дифф из 80% churn'а форматтера сжигает токены и маскирует баги. Артефакты сборки — только в .gitignore.
4. **Рефакторинг не смешивать с фичами.** Перемещение файла + его изменение git показывает как огромное «удалено/добавлено» — ревьюер не видит, что реально поменялось. Рефакторинги вливать и ревьюить отдельно.
5. **Момент запуска:** ветка feature-complete, тесты зелёные. Раньше — ревью обесценят следующие изменения; после релиза — уже бессмысленно.

### Цикл «дешёвые пишут — Fable проверяет»

main всегда стабилен; каждая фича — своя ветка, которую дешёвые модели исполняют по design doc; перед мержем фичи — `/code-review` medium Sonnet'ом (снимает грубое бесплатно для кредитов). Релизная ветка собирает фичи спринта; перед релизом — rebase на main, зелёные тесты, и только тогда один проход Fable 5 `/code-review` high. Дорогая модель видит компактный чистый дифф из одной логики — ровно те условия, в которых она находит пропущенное Sonnet'ом.
