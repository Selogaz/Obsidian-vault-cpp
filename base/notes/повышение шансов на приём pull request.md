Шанс на приём pull request растёт, когда изменение нужно мейнтейнерам, маленькое, сделано в их стиле и легко проверяется. **AI-шные PR приносят в среднем примерно в 1,7 раза больше проблем, поэтому ревьюеры смотрят на них настороженно**[^1].

## До кода

- Начинать с открытых issues (good first issue, help wanted, баги с воспроизведением): нужность изменения уже признана.
- Свою находку без issue сначала описать в issue и обсудить с мейнтейнерами.
- Прочитать CONTRIBUTING и проверить, есть ли политика по AI-коду.
- Прочитать definition of done в issue: частая потеря — пункт C из «A, B, C», который PR не закрыл[^1].

## Сам PR

- Одна задача — один маленький PR, без попутных «улучшений», рефакторингов и правок их `CLAUDE.md`.
- Код и коммиты в стиле проекта: соглашения брать из их `CLAUDE.md`, CONTRIBUTING и истории коммитов.
- Тест, который падал до правки и проходит после.
- Ревью своей правки в свежей сессии, лучше другой моделью. Сессия, которая писала код, свои ошибки видит плохо и не должна писать к нему тесты[^1].
- Отдельно проверить доступ к объектам: самая частая ошибка AI-кода — BOLA, когда тесты зелёные, а владельца объекта никто не проверил[^1].

## Описание с доказательствами

Блок доказательств позволяет ревьюеру сразу увидеть, что проверено, без детального чтения кода[^2]:

```markdown
## Доказательства
### Что проверено и как
- сценарий целиком: видео
- до и после: скриншоты
- API: curl с ответом
- логи прогона
### Что не проверено и почему
```
