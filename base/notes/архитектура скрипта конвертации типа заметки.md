Как устроен макрос `templates/macros/convert-type.js` (команда QuickAdd `convert type`, `alt+shift+x`) и его тесты `templates/macros/convert-type.test.js`. Инструкция для пользователей лежит отдельно, в [[конвертация типа заметки]].

## Задача

Тип заметки в хранилище задают сразу три вещи: тег типа, папка и шаблон. Шаблон Templater даёт свойства, вкладки и каркас тела. Сменить тип значит согласованно поменять все три и при этом не потерять ничего из того, что уже есть в заметке: текст, свойства, входящие ссылки.

Перенести файл в другую папку недостаточно. Шаблон папки срабатывает только при создании файла, а при переносе – нет.

## Конвейер

Скрипт – одна функция, которая выполняет шаги строго по порядку. До шага 7 файл не меняется:

1. **Проверки.** Есть открытая `.md`-заметка, она не лежит в `templates/` или `base/categories/`, Templater доступен.
2. **Чтение.** Открытый редактор сохраняется, файл читается, старые свойства разбираются. Если YAML битый, команда сразу останавливается.
3. **Выбор.** Меню группы, затем меню подтипа. Подтипы собираются из манифестов.
4. **Сборка шаблона в строку.** Для типов с шаблоном её делает Templater, для атомарных заметок свойства собираются из манифеста.
5. **Слияние свойств.** Старые значения переносятся в пустые поля, `aliases` объединяются, `created` сохраняется, теги атомарных заметок отбираются, ссылки на саму себя убираются, недостающие мета и проблема спрашиваются.
6. **Слияние тела.** Из старого текста убираются шаблонные вкладки и пустые шаблонные разделы, из нового каркаса – заголовки, которые в тексте уже есть.
7. **Перенос и запись.** Сначала файл переносится в папку типа, потом в него один раз записывается новое содержимое.

## Решения и почему они такие

### Типы берутся из манифестов, а не из кода

Меню строится обходом папок `templates/create/…`. Подтип – это папка с `manifest.md`, а у типов с шаблоном ещё и с `template.md`. Название берётся из `name`, папка назначения – из `enforce_folder` подтипа или его корня.

- **Почему.** Новый подтип, добавленный в `templates/create`, сам появится в меню, а переименование папки в манифесте не потребует правки скрипта. Это тот же источник истины, по которому работают валидатор и скрипты создания (`contacts.js`, `sources.js`). Так конвертация не разойдётся с обычным созданием.
- **Что в коде всё-таки задано явно**
	- группы и их корни. Корни раскиданы по разным папкам: люди – это сразу три корня, а системные типы вложены друг в друга (`meta/problem/hierarchy`). Перечислить пять групп проще и надёжнее, чем вычислять их.
- **Исключения.** Longform-проекты нельзя выбрать: их шаблон строит папку сцен и сам переносит файл (`tp.file.move`), а один переносимый файл эту структуру не заменит. Категорий нет ни в меню, ни среди обрабатываемых заметок: это единственная часть хранилища, которую ведёт только человек.
- **Подтип без манифеста** (например, папка `sources/zotero`) молча пропускается. Раньше из-за такой папки меню источников падало целиком.

### Шаблон собирается в строку, без временного файла

Для типов с шаблоном используется внутреннее API Templater: `start_templater_task`, затем `read_and_parse_template(create_running_config(шаблон, заметка, 0))` и `end_templater_task` в `finally`.

- **Почему.** Вопросы шаблона (категория, мета, статус) появляются ровно так же, как при обычном создании. `tp.user.manifest()` по-прежнему находит манифест через `tp.config.template_file`.
- **Почему не временный файл.** Первая версия создавала временную заметку "(converting)" и удаляла её. Из-за этого в списке файлов мелькала лишняя заметка, другие плагины реагировали на создание файла, а при сбое мог остаться мусор.
- **Почему `start/end_templater_task`.** Без них не срабатывают хуки `on_all_templates_executed`. От них зависит, например, `cursor.js`.
- **Цена.** Это внутреннее API, и после обновления Templater оно может измениться. Публичного способа собрать шаблон в строку нет, а скрипты создания тоже пользуются внутренним `create_new_note_from_template`. Если API пропадёт, скрипт сразу покажет "Templater is not available" или ошибку и не тронет заметку.
- **Атомарные заметки** собираются без Templater. У них нет шаблонов по подтипам: общий шаблон `notes/template.md` выбирает тип по префиксу и сам переименовывает файл, поэтому для конвертации он не годится. Свойства собираются из манифеста подтипа: тег берётся из `target.query`, `icon` и `color` – из `fields`. Набор полей у всех 23 подтипов одинаковый.

### Одна запись: либо всё, либо ничего

Свойства и тело собираются в памяти, и файл получает один `vault.modify`.

- **Почему.** В ранней версии свойства дописывались вторым шагом через `processFrontMatter`. Если этот шаг падал, заметка оставалась наполовину сконвертированной, а старые `aliases` и `created` пропадали. Теперь любая ошибка до записи (в шаблоне, в YAML, отмена) оставляет файл байт в байт прежним. Это проверяют тесты.
- **Почему сначала перенос, потом запись.** Если упадёт перенос, файл не изменится вовсе. Если упадёт запись, файл уже будет в новой папке, но со старым содержимым. Это видно сразу и не теряет данных. При обратном порядке заметка могла бы остаться с новым типом в чужой папке.
- **Почему `fileManager.renameFile`, а не копия.** Это тот же файл, поэтому Obsidian обновляет входящие ссылки, включая ссылки с путём `[[base/notes/x|…]]`. Свободное имя на случай совпадения подбирает `vault.getAvailablePath`.

### Старое читается до вопросов

Сначала сохраняется открытый редактор, затем файл читается и разбирается, и только после этого показываются меню.

- **Сохранение.** Obsidian пишет правки на диск с задержкой. Без явного `save()` текст, набранный за последние секунды, был бы затёрт.
- **Разбор до меню.** При битом YAML пользователь не должен отвечать на вопросы шаблона впустую.
- **Свойства читаются из текста файла, а не из `metadataCache`.** Кэш может отставать, а при битом YAML он пустой. Из-за этого старые свойства молча терялись бы.
- **Функции Obsidian вместо регулярных выражений**
	- `getFrontMatterInfo`, `parseYaml`, `stringifyYaml`. Они правильно обрабатывают пустые свойства `---\n---`, CRLF и заметки без свойств. Первая регулярка на этих случаях ломалась.

### Слияние свойств

- **Основа – свойства нового типа**, которые собрал шаблон. Всё, чего у нового типа нет, отбрасывается. Иначе источник, переведённый в заметку, тащил бы за собой `status`, `rating`, `url`, и валидатор считал бы их лишними.
- **Старое значение переносится в любое поле нового типа, которое осталось пустым.** Пустым считаются `null`, `''`, `false` и `[]`. Так книга → статья сохраняет `rating`, `url`, `start`, `creator`, а Working → Client сохраняет `production` и `relevant`. Раньше переносились только `description` и `created`, и всё остальное заменялось пустыми значениями. Если же шаблон что-то спросил и получил ответ (например, статус), новое значение важнее: пользователь только что выбрал его сам. `relevant: false` из шаблона считается пустым, потому что это значение по умолчанию, а не выбор пользователя.
- **`tags`, `aliases`, `icon`, `color`, `created`, `updated` (`OWN_KEYS`) так не переносятся.** У каждого из них своё правило:
	- `aliases` объединяются без повторов;
	- `created` всегда остаётся прежним, потому что заметку не создали заново;
	- `updated` ставит шаблон;
	- `icon` и `color` принадлежат типу;
	- `tags` задаёт тип.
- **Атомарные заметки сохраняют теги `category/…` и `mark/…`.** Для них это часть смысла заметки: категория и колода Anki, отметки вроде `mark/approved`. Остальные теги отбрасываются, потому что у типов с шаблоном теги задаёт шаблон. Теги разбираются в любой записи: списком, строкой через запятую или с `#`. Это тот же разбор, что `tagsOf` в `change-deck.js`.

### Ссылки на саму себя и недостающая мета

Скрипты шаблонов `context.js`, `meta.js` и `problem.js` подставляют место в иерархии автоматически. Для обычного создания это правильно, а при конвертации даёт два побочных эффекта:

1. **Открытая структурная заметка наследует саму себя.** Если конвертировать мету, `meta.js` подставит её же как мету. Поэтому из `category`, `meta` и `problem` удаляются ссылки, которые указывают на конвертируемый файл. Проверяется через `getFirstLinkpathDest`, так что ловятся все записи: `[[x]]`, `[[path/x|alias]]` и просто имя.
2. **Свойства самой заметки принимаются за "заранее заполненное место".** `context.js` умеет брать место из свойств создаваемой заметки. Это сделано для представления Structure, которое пишет свойства до шаблона. Когда у конвертируемой заметки уже есть `category`, место считается заполненным, и мету не спрашивают вовсе.

Чинить это в общих скриптах не стал: на них держатся обычное создание и Structure. Вместо этого макрос после шаблона сам спрашивает пустые `meta` и `problem`. Варианты отбираются по тем же правилам, что в манифесте: мета из той же категории, проблема из той же меты. Сама заметка в списке не появляется, `mark/ignore` пропускается, закреплённые (`relevant`, 📌) стоят первыми. Esc оставляет поле пустым: манифест это разрешает. Минус такого решения: если пользователь нажал Esc в вопросе шаблона нарочно, его спросят ещё раз. Отличить пропущенный вопрос от отказа здесь нельзя.

Категорию макрос сам не спрашивает. Её либо берёт `context.js` из свойства заметки, либо спрашивает шаблон. Теги `category/…` атомарных заметок в свойство `category` не превращаются, это осознанно отложено.

### Слияние тела

Итоговое тело складывается так: каркас нового шаблона, затем старый текст. Без правил на стыке получаются дубли, поэтому правил три. Все они удаляют только то, что дословно пришло из шаблона, а текст пользователя не трогают.

1. **Вкладки.** Старый блок `~~~~tabs … ~~~~` в начале текста удаляется, только если он дословно совпадает с блоком вкладок одного из шаблонов в `templates/create`. Вкладки, написанные или изменённые вручную, остаются. Первая версия удаляла блок всегда и могла молча стереть текст внутри вкладок. Проверка по хранилищу показала, что у всех заметок с вкладками в начале блок совпадает с нынешними шаблонами, так что дублей это правило не оставит.
2. **Заголовки каркаса.** Шаблоны проектов кладут в тело `# Description` и `# Tasks`. Из нового каркаса удаляются заголовки, которые уже есть в старом тексте, а из старого текста – пустые разделы с шаблонными заголовками, если у нового типа таких заголовков нет. Без этого при каждой конвертации проекта копилась новая пара заголовков. Разделы с текстом остаются всегда.
3. **`💤`.** Заглушка системных шаблонов добавляется, только если старый текст пустой.

Метки курсора `<% tp.file.cursor() %>` вырезаются из собранного шаблона: заметка не открывается в режиме вставки шаблона, и метка осталась бы в тексте. Переводы строк в теле приводятся к LF: свойства и так пишутся с LF, а смешанные окончания строк в одном файле только мешают.

### Стиль

Скрипт написан в манере соседних макросов `templates/macros/`: два пробела, точки с запятой, одинарные кавычки, стрелочные функции, ранний `return` с `Notice`. Отличие одно, и оно намеренное: в коде нет комментариев, по желанию автора. Поэтому всё объяснение собрано в этой заметке. Загрузчик типов не вынесен в общий помощник вместе с `contacts.js` и `sources.js`: это затронуло бы чужие скрипты создания.

## Тесты

### Как устроены

Тесты – это один файл JavaScript: асинхронная функция, которую запускают в работающем Obsidian:

```
obsidian eval code="$(cat templates/macros/convert-type.test.js)"
```

Результат – строка вида `44/44 passed` и список PASS/FAIL. Если перед запуском выполнить `obsidian eval code="window.__convTestKeep=true"`, сконвертированные заметки останутся, и их можно проверить через `vault.py check`. Следующий обычный прогон их удалит.

**Почему тесты идут в живом Obsidian, а не в Node с заглушками.** Почти всё поведение скрипта определяют чужие системы: Templater собирает шаблоны и задаёт вопросы, `metadataCache` разрешает ссылки, `renameFile` обновляет входящие ссылки, плагины хранилища реагируют на запись. Заглушки проверяли бы только мои представления о них. Именно живой прогон нашёл баги, которых не видно в коде: падение на подтипе без манифеста, `url`, который плагин превращает в список, вмешательство триггера папки Templater.

**Почему файл лежит рядом со скриптом.** В хранилище нет места для тестов макросов, а новые папки создавать нельзя. `templates/macros/` не папка пользовательских функций Templater, и QuickAdd вызывает только явно указанные скрипты, поэтому тест нигде не зарегистрирован и сам не запустится.

### Как скрипт запускается в тестах

- **Скрипт каждый раз читается из файла** и выполняется через `new Function`. Тесты всегда проверяют текущую версию, без кэша `require`.
- **Меню QuickAdd заменены заглушкой.** На каждое меню она выдаёт заранее заданный выбор: подпись, функцию или `null` для отмены. Тест получает все показанные меню и может проверить их состав и порядок.
- **Вопросы шаблонов** – это окна Templater. Таймер закрывает их клавишей Escape каждые 100 мс, и они возвращают пустое значение. Поэтому в тестах категория и мета из вопросов остаются пустыми, а заполненные значения приходят из свойств фикстур.
- **`Notice` перехвачен:** уведомления собираются в список для проверок и не всплывают в интерфейсе.
- **Модуль `obsidian`** берётся у Templater, которому скрипт и так нужен, а не у Excalidraw. Так у тестов нет лишней зависимости.

### Безопасность для работающего Obsidian

Тесты выполняются в настоящем приложении, поэтому правила здесь жёсткие. Одно нарушение уже случилось: оставшийся работать таймер закрывал у пользователя все окна до перезагрузки.

- **Таймер Escape и все подмены** (`getActiveFile`, `read_and_parse_template`) снимаются в `finally`. Номер таймера хранится в `window.__convTestTimer`, и перед стартом остаток прошлого прогона гасится.
- **Последняя проверка набора** открывает обычное окно и через 1,5 с убеждается, что оно не закрылось.
- **Файлы тестов** – только `zz convtest*`. Они удаляются в начале и в конце прогона, и последняя проверка подтверждает, что не осталось ни одного. Чужие заметки не трогаются. Тесты не перезагружают приложение и не выключают плагины.
- **Защищённые пути** (`base/categories/`, `templates/…`) проверяются на поддельном объекте файла. Создавать что-то в категориях нельзя даже временно.

### Надёжность

- **Записи дожидаются, а не ждут фиксированное время.** Функция `settle` ждёт, пока у файлов перестанут меняться время изменения и размер и появится кэш метаданных. После записи на файл реагируют другие плагины: например, к проектам добавляются теги `priority/normal` и `status/wip`. Фиксированная пауза здесь то не дождалась бы конца, то тратила бы время зря.
- **Фикстуры, где есть только свойства, создаются в два шага.** Триггер папки Templater срабатывает на новые файлы в `base/notes` и однажды переименовал чужую фикстуру. Поэтому такие заметки сначала создаются с текстом-заглушкой, а настоящее содержимое записывается потом.
- **Блоки вкладок в фикстурах – настоящие**, их тесты читают из шаблонов при старте. Скрипт удаляет только вкладки, дословно совпадающие с шаблоном, поэтому выдуманный блок проверял бы не то.
- **"Сегодня" проверяется в момент проверки**, а не вычисляется один раз при старте. Иначе тест упал бы около полуночи.
- **Порядок тегов сравнивается после сортировки**
	- другие плагины его меняют. **`url` сравнивается как список:** по манифесту источников это список, и плагин хранилища приводит строку к нему.
- **Тесты нужно запускать по порядку.** Несколько тестов отмены используют одну заметку и проверяют, что она не изменилась. Тест на совпадение имени опирается на соседний файл. Это оставлено ради простоты.

### Что покрыто

Набор из 44 проверок. Каждая проверяет путь, тип, свойства и тело результата.

- **Все группы**
	- контакт, автор, компания, проект Single и Short, книга, мета, проблема, иерархия, атомарные заметки из basic, discourse и specific.
- **Перенос свойств:**
	- `aliases`: объединение, пустой список, строка вместо списка;
	- `created`: сохраняется, а если его не было – ставится сегодняшняя дата;
	- `description`;
	- конвертация внутри одной группы
		- книга → статья, Working → Client прямо в той же папке;
	- удаление свойств, которых нет у нового типа;
	- `deck`, `cssclasses`, теги `category/` и `mark/` у атомарных заметок, включая запись строкой и с `#`.
- **Тело:**
	- шаблонные вкладки удаляются, свои остаются;
	- CRLF;
	- заглушка `💤` при пустом и непустом тексте;
	- `# Description` и `# Tasks` не копятся при повторных конвертациях проекта;
	- пустые разделы удаляются, разделы с текстом остаются.
- **Связи:**
	- ссылка на саму себя во всех формах
		- из контекста Templater, из собственных свойств, с путём и псевдонимом, просто именем;
	- вопрос о недостающей мете (из той же категории, без самой заметки) и о проблеме (из выбранной меты).
- **Файлы и ссылки:**
	- перенос в нужную папку;
	- конвертация без переноса, когда заметка уже в своей папке;
	- свободное имя при совпадении, при этом чужой файл остаётся байт в байт прежним;
	- входящие ссылки `[[имя]]` и `[[путь/имя|текст]]` после переноса.
- **Входные крайности**
	- пустые свойства `---\n---`, заметка без свойств, битый YAML (команда останавливается до меню), текст в редакторе, ещё не сохранённый на диск.
- **Меню**
	- порядок групп
	- в меню проектов нет longform, категорий нет нигде
	- Primary первым среди атомарных заметок.
- **Отказы и ошибки:**
	- отмена в первом и во втором меню;
	- нет открытой заметки, открыт не `.md`-файл, защищённые пути;
	- ошибка при сборке шаблона и шаблон, который сам бросает ошибку.

Во всех этих случаях заметка остаётся байт в байт прежней, и в Templater не остаётся незакрытой задачи.
