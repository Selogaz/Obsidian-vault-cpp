## Что такое worktree-изоляция

**Проблема.** Обычно у git-репозитория одно рабочее дерево (working tree) — папка с файлами. Три агента, правящие SCSS одних секций в одной папке, затрут друг друга: агент B перезапишет файл, который правил агент A, — гонка и потерянные изменения.

**Решение — `git worktree`.** Одна команда `git worktree add <путь> -b <ветка>` создаёт **вторую (третью, …) рабочую папку того же репозитория**, привязанную к своей ветке. Ключевое:

- Все worktree делят **одну общую историю** (`.git` объектную базу) — это не `git clone`, диски не дублируются на всю историю.
- Но у каждого — **свой набор файлов на диске и своя ветка**. Правки в `bite-wt-4a` физически не видны в `bite-wt-4b1`, пока не смёржишь ветки.

**Как это выглядит у нас:**

```
bite-transit-static/   ← основной worktree (ветка homepage) — не трогается
bite-wt-4a/            ← ветка verify/4a  — агент 4.A
bite-wt-4b1/           ← ветка verify/4b1 — агент 4.B-1
bite-wt-4b2/           ← ветка verify/4b2 — агент 4.B-2
```

Каждый агент правит SCSS в своей папке → **конфликтов нет by construction**. `node_modules` я симлинкнул из основного репо (263M — общий, а не ×3 копии).

**Когда вернётесь — сведение:**

- посмотреть, что каждый наменял: `git -C bite-wt-4a diff` (и т.д.);
- смёржить нужное в `homepage`: `git merge verify/4a` — если 4.A и 4.B правили разные строки, конфликтов не будет; если одни — git покажет конфликт, решите вручную;
- убрать worktree после мёржа: `git worktree remove bite-wt-4a` (авто-удаляется, если ветка смёржена и дерево чисто).

**Цена** (почему это не «всегда включать»): ~200–500 мс на создание + место под рабочую копию файлов (не истории). Оправдано ровно когда агенты **параллельно мутируют пересекающиеся файлы** — как здесь. Для одиночного агента или read-only задач worktree не нужен.
