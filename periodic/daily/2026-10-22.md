# Абстрактный

В чём разница между абстрактным классом и интерфейсом в Java? Когда вы выберете одно, а когда другое?
Абстрактный класс может хранить состояние, интерфейс задаёт контракт, то есть обязательство. Наследоваться можно только от одного класса, а реализаций интерфейсов можно сделать сколько угодно. Абстрактный класс - это отношение "является", интерфейс - "умеет". Для общих черт у классов лучше сделать абстрактный класс, чем таскать поля по дочерним. Интерфейс нужен там, где нужно описать способность или роль. Условно, для телефонов лучше сделать абстрактный класс. А вот для функций интернета, фото или воспроизведения мелодий лучше сделать интерфейс.

# Equals hashcode

equals сравнивает по содержимому, hashCode нужен для коллекций. По умолчанию equals сравнивает ссылки как `'=='`, а hashcode вычисляется по идентичности объекта, а не по полям
Если a.equals(b), то обязательно равны и хэшкоды. Обратное не требуется, у разных объектов могут быть одинаковые хэши, это [[java коллизия|коллизия]].
Почему [[HashMap]] ломается: [[HashMap]] сначала по хэш-коду выбирает бакет, а уже внутри бакета сравнивает по equals. Если 2 равных по equals объекта дают разные хэши, то до equals дело не доходит.
Отсюда вывод: не стоит использовать изменяемый объект как ключ. Если изменить поле, от которого зависит hash, после put, то объект "потеряется" в мапе, вернется null при попытке получения. А хэшсет пропустит дубликаты.

# Тестирование

Smoke проверяет базовую работоспособность, регрессионное – что старое не
	сломалось. Еще есть unit-тестирование, интеграционное, нагрузочное. В Java для этого используются JUnit и Mockito. Классификация:
	- по уровню
		- unit-интеграционное-системное-приёмочное
	- по назначению
		- функциональное и нефункциональное(нагрузочное, производительность, безопасность, юзабилити, совместимость)
	- по знанию кода
		- черный, белый и серый ящик
	- по моменту и цели
		- smoke, sanity, регрессионное, retest
	- по способу
		- ручное и автоматизированное

Нагрузку тестируют в JMeter или Gatling. JUnit - фреймворк для запуска тестов, Mockito - заглушки(моки) зависимостей в unit-тестах.
Сравнение smoke и регрессии:
- когда
	- smoke - на каждую новую сборку, регрессия - после изменений, перед релизом
- объем
	- smoke - несколько критичных сценариев за минуты, регрессия - широкий набор за часы
- цель
	- smoke отвечает можно ли вообще тестировать эту сборку, регрессия - "не сломали ли изменения то, что работало"
- регрессия - главный кандидат на автоматизацию. Она повторяется на каждый релиз, руками это долго и дорого.

Сам ответ:
"Классифицировать можно по уровням (unit, интеграционное, системное,
	▎ приёмочное), по функциональности (функциональное и нефункциональное,
	▎ например нагрузочное в JMeter), по доступу к коду (чёрный и белый ящик).
	▎ Smoke – быстрая проверка критичного пути на новой сборке: можно ли её вообще
	▎ тестировать. Регрессия – широкая проверка, что изменения не сломали
	▎ существующее. Её гоняют на каждый релиз, поэтому её в первую очередь и
	▎ автоматизируют".

# Page Object

Page Object – класс на страницу, внутри локаторы и методы-действия. Одно место для локаторов, тесты читаются как сценарий, легко поддерживать, компоненты переиспользуются.

Почему Thread.sleep плох – две причины, а не одна:
	- медленно
		- если элемент появился за 0,5 с, мы всё равно ждём 5 с, а на сотнях
		тестов это минуты и часы прогона;
	- нестабильно (flaky): если на медленном CI элемент грузился 6 с, тест падает,
		хотя бага нет
	- Implicit wait – глобальная настройка драйвера
		- findElement ждёт появления
		 элемента до N секунд. Работает только на поиск элемента, а не на его
		 состояние (кликабельность, видимость).
	- Explicit wait – ожидание конкретного условия для конкретного элемента:
	new WebDriverWait(driver, Duration.ofSeconds(10))
		- Explicit wait решает обе проблемы
			- продолжает сразу, как только условие выполнено, и ждёт до таймаута, если нужно.
	- Fluent wait – тот же explicit, но с настройками
		- частота опроса (polling) и исключения, которые нужно игнорировать (например, NoSuchElementException)
	- не смешивайте implicit и explicit. Время ожидания может складываться непредсказуемо. Обычно
		 оставляют только explicit.
- Selenide ждёт сам
	- $("#submit").shouldBe(visible).click(). По умолчанию 4 секунды.
